# 研究案例 02｜CabLate

研究時間：2026-11-24～25（本輪歷史快照）

公開入口：[Threads @cab_late](https://www.threads.com/@cab_late) ｜ [個人官網](https://cablate.com/about/) ｜ [CabAI 公開原碼](https://github.com/cablate/cabai) ｜ [實作文章](https://cablate.com/articles/)

## 為什麼研究他

依本人官網介紹，CabLate 曾從事全端工程、系統設計與產品實作，2025 年 6 月起全職投入 AI 應用、教學、內容與數位產品。追蹤他的公開內容，可以了解 Agent、Skills、上下文管理、工作流防錯及多模型協作的實務取捨，而不只是工具的新功能。

這次除了讀他自己的文章，也讀了 Threads 回覆分頁，觀察他如何解釋、反駁或補充別人的觀點，再對照官網方法文章和 CabAI 的公開實作。研究目的不是複製他整套工具，也不是課程推薦或人物排名，而是找出一個值得帶回既有工作流程的差距。

- [EVIDENCE.md](EVIDENCE.md)：代表性公開證據及查核邊界。
- [POST.md](POST.md)：文章狀態及主要公開來源。

## 本輪選擇：先衡量委派的價值

研究者先對 AI 使用健檢感興趣，進一步要求只挑一個自己既有做法還沒有充分做到的關鍵點。分工作區、文件化、部分防錯及多 AI 討論並非全新的概念，因此本次不再逐一介紹。

C02 的文章提供另一個角度：不同代理需要重建脈絡，成果帶回來後又可能需要主對話核對；投入增加不一定換到新增價值。可試著記錄委派前期待取得的成果、實際用量或耗時、帶回的新增證據／不同判斷，以及驗收與返工是否抵銷收穫。

### 最小驗證

下一次研究只挑一個重要缺口。先寫下另一個 AI 預期帶回的東西；若只是重複摘要，留在主對話即可。完成後比較實際新增的可用資訊和驗收投入；若平台未提供用量，明列未知，不將 token 數直接等同實際費用。一次比較不代表普遍效益，也不必先建記錄系統。

### 反例與邊界

獨立反證本來就可能需要重讀同一來源；這種刻意重疊有價值，不能只用 token 多寡判斷。反之，較少 token 不代表判斷正確。C11–C13 顯示部分驗收與權限檢查可以由程式處理，但不證明所有人工或 AI review 都能被取代。

## 寫作取捨

人物誌聚焦一個可遷移的做法，簡述公開背景與值得追蹤的內容。其他發現留在證據頁，不塞進同一篇。所提出的改善仍是待嘗試的想法，不能寫成已採用或已有成效。依[有限度編輯原則](../../METHOD.md#從研究到文章)整理，待本人確認文章措辭。
